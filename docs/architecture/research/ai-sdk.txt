* [high] reasoning.effort na Responses API: passado como body { "reasoning": { "effort": "low" } }; conjunto completo de valores = none, minimal, low, medium, high, xhigh, max, mas o subconjunto aceito depende do modelo: GPT-5.6 (sol/terra/luna) = none/low/medium/high/xhigh/max; gpt-5.4-mini e nano = none (default)/low/medium/high/xhigh; gpt-5.5 default = medium; 'minimal' é legado (era gpt-5/5.1); 'max' aparece documentado apenas na família 5.6
  Guia oficial de reasoning: "Some models support only a subset of these values, so check the relevant model page". Orientação oficial: medium como ponto de partida balanceado, low para latência, high/xhigh quando reasoning melhora qualidade mensuravelmente, max para "hardest quality-first workloads". No AI SDK: providerOptions: { openai: { reasoningEffort: 'high' } } (ou opção padronizada `reasoning` no v7).
* [high] SSE/streaming em Next.js App Router self-hosted atrás de Nginx: no location do proxy usar proxy_buffering off; proxy_cache off; proxy_http_version 1.1; proxy_set_header Connection ''; proxy_read_timeout alto (ex. 300s); e/ou enviar do app o header X-Accel-Buffering: no (Nginx desativa buffering por-resposta ao vê-lo) + Cache-Control: no-cache, no-transform
  No AI SDK, os headers são passados em createUIMessageStreamResponse({ headers: { 'X-Accel-Buffering': 'no', 'Cache-Control': 'no-cache, no-transform' } }) (v7) ou result.toUIMessageStreamResponse({ headers }) (v5/v6). A abordagem via header X-Accel-Buffering é preferível por ser por-rota, sem mexer na config global do Nginx. Atenção: gzip/compressão no Nginx também bufferiza — desativar compressão para a rota de streaming (no-transform ajuda contra proxies intermediários). No route handler, garantir runtime Node (export const runtime = 'nodejs') e resposta dinâmica (export const dynamic = 'force-dynamic'). PM2 não interfere no streaming.

=GOTCHAS=
- ai@7 é ESM-only e exige Node >=22 — scripts CommonJS (ex.: jobs utilitários com require) quebram; a linha v6 (Node >=18, não-ESM-only) é o fallback mantido.
- Os majors de ai e @ai-sdk/openai andam pareados: ai v7 ↔ @ai-sdk/openai 4.x, ai v6 ↔ 3.x, ai v5 ↔ 2.x. Misturar linhas causa erros de provider specification.
- zod 4 no peer range começa em 4.1.8 — zod 4.0.x NÃO satisfaz o peer do AI SDK (satisfaz o do SDK openai oficial, que aceita ^4.0).
- Valores de reasoning.effort variam por modelo: 'max' só na família GPT-5.6; 'minimal' é legado; gpt-5.4-mini/nano têm default 'none' (sem reasoning) — enviar 'medium' sem querer aumenta custo/latência no perfil barato.
- X-Accel-Buffering: no resolve o buffering do proxy_pass do Nginx, mas NÃO desativa gzip — compressão ativa na rota de SSE ainda bufferiza; usar no-transform e excluir a rota do gzip.
- Agregadores de preço de terceiros mostraram números conflitantes/desatualizados para GPT-5.x (ex.: gpt-5.2 com dois preços diferentes) — sempre conferir developers.openai.com/api/docs/pricing.
- No v7, mensagens system dentro do array messages são rejeitadas por padrão (usar instructions ou allowSystemInMessages: true) — fonte comum de erro em código migrado.
- Preços 'pro' (gpt-5.5-pro/gpt-5.4-pro a $30/$180) são ~6x o flagship — não usar como default de perfil aprofundado num app de flashcards.
=RECOMMENDATIONS=
- Instalar ai@^7.0.32 + @ai-sdk/openai@^4.0.16 + zod@^4.4.3 (peer exige zod >=4.1.8 na linha 4). O stack do usuário (Node 22.23.1, Next 16.2.x, React 19.2.4) atende os requisitos do v7 (Node >=22, ESM). Se quiser evitar ESM-only e as renomeações do v7, ai@6.0.231 + @ai-sdk/openai@3.0.86 é a linha estável anterior, ainda com patches e mesmo suporte a zod 4 e Responses API.
- Usar a Responses API via provider default: openai('gpt-5.4-mini') já usa Responses. Perfil rápido/barato (explicações/sugestões de cards): gpt-5.4-mini com providerOptions.openai.reasoningEffort: 'none' ou 'low' (none é o default do modelo — latência mínima); gpt-5.4-nano para sugestões triviais em lote. Perfil aprofundado: gpt-5.6-terra com reasoningEffort 'high' como padrão custo-eficiente, escalando a gpt-5.6-sol + 'xhigh'/'max' apenas onde qualidade mensuravelmente importa.
- Structured outputs para sugestões de cards: generateObject (ou output no streamText v7) com schema zod 4 + strictJsonSchema: true — totalmente suportado na Responses API.
- Streaming: no route handler do App Router, retornar o UI message stream com headers { 'X-Accel-Buffering': 'no', 'Cache-Control': 'no-cache, no-transform' } (createUIMessageStreamResponse no v7; toUIMessageStreamResponse no v5/v6) e no Nginx do location da API: proxy_buffering off; proxy_cache off; proxy_http_version 1.1; proxy_set_header Connection ''; proxy_read_timeout 300s; desativar gzip para essa rota. export const runtime = 'nodejs' e dynamic = 'force-dynamic' no handler.
- Embeddings: text-embedding-3-small ($0.02/1M) com embedMany do AI SDK; para pgvector, considerar dimensions: 512 ou 1024 para índices menores com perda mínima — não esperar modelo novo, a série 3 segue sendo a atual.
- Preferir AI SDK ao SDK openai oficial neste projeto: o app tem UI de chat/streaming e tools server-side, exatamente o caso onde o AI SDK elimina o loop manual de function calling e o protocolo de stream custom. Manter o SDK oficial apenas se surgir necessidade de um recurso da Responses API ainda não exposto pelo provider (checar providerOptions antes de assumir que falta).
- Ao migrar exemplos/docs antigos para v7, rodar npx @ai-sdk/codemod v7 e atentar para: system→instructions, onFinish→onEnd, usage agora agregado (finalStep.usage para o último step), toUIMessageStreamResponse deprecado.
=CORRECTIONS=
! CLAIM: Contexto tipado por tool via contextSchema + runtimeContext (detail da alegação sobre breaking changes do AI SDK 7)
  FIX: O nome da opção está errado. O contexto tipado POR TOOL usa `contextSchema` (declarado na tool) + `toolsContext` (no call-site de generateText/streamText, com valores por tool, ex.: toolsContext: { weather: { apiKey } }). `runtimeContext` existe no AI SDK 7, mas é uma opção separada para dados de runtime COMPARTILHADOS entre todas as tools — não é o mecanismo de contexto tipado por tool. Além disso, o antigo `experimental_context` do callback da tool virou `context` (estável). Se o autor codificar `runtimeContext` esperando validação pelo contextSchema por tool, o valor não chega à tool. [https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0 (exemplo de código oficial mostra contextSchema na tool e toolsContext no call-site, com runtimeContext como opção distinta para dados compartilhados)]
