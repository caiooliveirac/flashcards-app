* [high] Anki true retention: pass rate (Hard/Good/Easy vs Again) on the first review of each card per day, split young/mature at 21 days; with FSRS it should approximate desired retention
  Anki manual (docs.ankiweb.net/stats.html): the True Retention table in Statistics counts only the first review of a card each day; Again = fail, Hard/Good/Easy = pass; 'mature' = interval >= 21 days, 'young' < 21 days; shown across multiple time frames. With FSRS enabled 'your true retention is expected to be close to your desired retention'; single-day windows are noisy — the manual recommends evaluating over at least a month. It is the recommended way to check whether FSRS is calibrated for the user (compare true retention vs desired retention and adjust).

  Anki manual (deck-options.html, FSRS section): default desired retention 90%, described as a good balance of retention and workload; above 90% 'the workload increases very quickly' and users are advised to keep it below 0.97; commonly cited practical band is 0.80-0.95. ts-fsrs mirrors this: default_request_retention=0.9. =GOTCHAS=
- ts-fsrs repo is now a monorepo; the core package source lives in packages/fsrs and the optimizer is a separate npm package @open-spaced-repetition/binding — do not look for optimizer APIs inside ts-fsrs itself.
- fsrs-rs-nodejs GitHub shows v0.9.1 (2026-06-13) but npm latest is still 0.9.0 (2025-03-22) — the npm artifact lags the repo.
- Rating.Manual=0 exists in ts-fsrs; manual reschedules/forgets land in review logs and must be filtered out before training.
- Card.elapsed_days and ReviewLog.elapsed_days/last_elapsed_days are deprecated in current ts-fsrs typings; compute elapsed time from last_review/review timestamps instead.
- ts-fsrs requires Node >= 20 (fine on Node 22.23.1); @open-spaced-repetition/binding also requires Node >= 20 and does not run on edge runtimes; in browsers it needs COOP/COEP headers.
- FSRS-6 decay is learnable (w[20], default 0.1542) — do not hardcode the old FSRS-4.5 decay of 0.5 in any retrievability math; use ts-fsrs's forgetting_curve/get_retrievability instead of reimplementing.
- Anki removed 'compute minimum recommended retention' in 25.07 — don't clone that feature; CMRR is no longer the community-endorsed workflow.
- ts-fsrs default_enable_fuzz is false — enable it explicitly if you want Anki-like interval fuzzing (applies only to intervals >= 2.5 days).
- ishiko732/ts-fsrs-demo dropped Prisma for Kysely in 2025; older tutorials referencing its prisma/schema.prisma are stale (file 404s on main).
=RECOMMENDATIONS=
- Use ts-fsrs@5.4.1 (exact) for scheduling. Store per-user parameters as a 21-number array (jsonb) plus desired_retention; build the scheduler with fsrs(generatorParameters({ w, request_retention, enable_fuzz: true, enable_short_term: true })). generatorParameters auto-migrates 17/19-length legacy arrays, so persisting raw arrays is safe across FSRS versions.
- For server-side parameter optimization use @open-spaced-repetition/binding@0.5.0 (MIT, same monorepo/author as ts-fsrs, wraps fsrs 6.5.0 crate). Run computeParameters in a worker_thread or child process with its timeout option on the 4 vCPU box; feed it items derived from the revlog table (exclude Rating.Manual=0 rows). Avoid fsrs-rs-nodejs (npm stuck at 0.9.0 since 2025-03) and fsrs-browser (browser/WASM target, needs COOP/COEP).
- Model the database after ts-fsrs-demo: a cards table (due, stability, difficulty, scheduled_days, reps, lapses, learning_steps, state, last_review, suspended, deleted) separate from notes, plus an append-only revlog (cid, grade, state, due, stability, difficulty, scheduled_days, learning_steps, review, duration). Do not build new logic on elapsed_days/last_elapsed_days — they are marked deprecated in current ts-fsrs models.
- Default desired retention to 0.90, clamp user input to roughly 0.70-0.97, and warn in the UI that workload rises steeply above 0.90. Keep learning steps sub-day (ts-fsrs defaults: learning ['1m','10m'], relearning ['10m']) and leave enable_short_term=true.
- Implement a 'true retention' stat the Anki way: per card per local day, take only the first review; pass = grade != Again; segment young (<21d interval) vs mature (>=21d); display over month+ windows and compare against desired retention as the calibration check. Use binding's computeOptimalSteps() if you want to suggest learning steps from the user's own data.
- Retrain parameters periodically (e.g., monthly or after a few hundred new reviews) rather than per-review; f.get_retrievability(card, now) gives R for display/sorting without rescheduling.

! CLAIM: binding API: convertCsvToFsrsItems(buffer, easeFactor, timezone, offsetFn)
  FIX: The second parameter is next_day_starts_at (i64) — the Anki-style hour at which the next day begins (README example passes 4, i.e. 4 AM day rollover) — not an ease factor. Misnaming it easeFactor would lead to passing a wrong value and silently mis-bucketing same-day reviews. [https://github.com/open-spaced-repetition/ts-fsrs/blob/main/packages/binding/src/convert.rs (lines ~119-128) and packages/binding/README.md]
! CLAIM: Forgetting curve: R(t,S) = (1 + FACTOR*t/(9*S))^decay
  FIX: The implemented code divides by S, not 9*S: forgetting_curve returns Math.pow(1 + (factor * elapsed_days) / stability, decay). The '9·S' appears only in a stale LaTeX doc comment in algorithm.ts. Note the claim's own conclusion R(S,S)=0.9 only holds for the actual (no-9) implementation given factor = e^(ln0.9/decay)-1, so the formula as written is internally inconsistent; the code behavior and the R(S,S)=0.9 statement are correct. [https://github.com/open-spaced-repetition/ts-fsrs/blob/main/packages/fsrs/src/algorithm.ts (computeDecayFactor lines 18-25, forgetting_curve lines 45-52)]
