* [high] Diferenças 0.6.0 -> 0.8.5 que importam: 0.7.0 (abr/2024) introduziu halfvec e sparsevec + binary_quantize, hamming_distance, jaccard_distance, l2_normalize, subvector, HNSW para L1; 0.8.0 (out/2024) introduziu iterative index scans (HNSW e IVFFlat), melhorou custo/planner e performance de HNSW (scan, insert, build on-disk); 0.8.1-0.8.5 são correções (suporte PG18, fix de buffer overflow em build paralelo HNSW, fixes de corrupção/repair de grafo HNSW no vacuum, memória em builds IVFFlat)
  Fonte: CHANGELOG.md do pgvector. * [high] Parâmetros atuais de índice: HNSW build m=16, ef_construction=64; query hnsw.ef_search=40 (default); iterative scan: hnsw.iterative_scan = off|strict_order|relaxed_order, hnsw.max_scan_tuples=20000 (default), hnsw.scan_mem_multiplier=1. IVFFlat: lists ~ rows/1000 até 1M linhas (sqrt(rows) acima), ivfflat.probes=1 default (~sqrt(lists) recomendado), ivfflat.iterative_scan=relaxed_order, ivfflat.max_probes
  Fonte: README.md do pgvector (master). Busca exata é o default e tem recall perfeito — índice ANN só quando a latência exigir.
* [medium] Guidance para o volume do app (milhares a dezenas de milhares de vetores POR USUÁRIO): com WHERE owner_id = X, três opções em ordem de simplicidade: (1) busca exata com índice btree em owner_id — se cada usuário tem <=~10-50k vetores, o scan exato do subconjunto do usuário costuma ser rápido o suficiente e tem recall 100%; (2) índice HNSW global + hnsw.iterative_scan=relaxed_order para compensar o filtro; (3) particionamento por owner se houver poucos tenants grandes. IVFFlat só compensa com dataset grande e estável (precisa treinar centróides com dados existentes); HNSW é o índice recomendado hoje (melhor recall/robustez, sem etapa de treino, build mais lento e mais memória)
  Armadilha de over-filtering documentada no README do pgvector: em índices aproximados 'filtering is applied AFTER the index is scanned' — um HNSW com ef_search=40 devolve no máx ~40 candidatos ANTES do WHERE; se o owner do filtro tem poucos vetores no meio do dataset global, o resultado pode vir vazio ou com recall péssimo. Mitigações oficiais: índice btree/exato na coluna de filtro (deixar o planner nem usar o ANN), partial index (poucos valores distintos), particionamento (muitos valores), ou iterative scans (0.8.0+) que continuam varrendo o grafo até juntar resultados suficientes (strict_order = ordem exata de distância, mais caro; relaxed_order = pode sair levemente fora de ordem, mais rápido; limitado por hnsw.max_scan_tuples). A recomendação (1) para escala por-usuário pequena é inferência minha a partir da guidance oficial de 'exact search é default e perfeito em recall' + números típicos, não uma frase literal da doc.
* [medium] Embeddings OpenAI atuais (jul/2026): continuam sendo text-embedding-3-small (1536 dims default) e text-embedding-3-large (3072 dims default), ambos com parâmetro dimensions para encurtar (Matryoshka); max input 8192 tokens; nenhum sucessor mais novo listado na doc oficial

Implicação pgvector: 3-large em 3072 dims NÃO é indexável como vector (limite 2000) — usar halfvec(3072) no índice, ou dimensions:1024/1536 na API; 3-small em 1536 indexa normal.
=GOTCHAS=
- O apt da Ubuntu 24.04 realmente só tem pgvector 0.6.0-1 — sem halfvec, sem iterative scans, e com bugs de HNSW/vacuum corrigidos apenas em 0.8.3+ (fixes de corrupção de índice). Ficar no 0.6 é risco real, não só falta de feature.
- Over-filtering com HNSW: o WHERE é aplicado DEPOIS do scan do índice; com ef_search=40 (default) a query devolve no máximo ~40 candidatos antes do filtro — filtro por owner pode devolver 0 linhas mesmo havendo matches. Solução: iterative_scan (0.8+), partial index, particionamento, ou busca exata no subconjunto do usuário.
- Limite de indexação: tipo vector indexa até 2000 dimensões — text-embedding-3-large (3072) exige halfvec (até 4000) no índice ou redução via parâmetro dimensions.
- pg-boss v11 NÃO tem migração automática a partir de v10 ou anterior (re-particionamento); como o projeto é novo isso não afeta, mas não instalar v10 'para depois subir'.
- pg-boss v12 é ESM/TS com named export — `import PgBoss from 'pg-boss'` (default import) quebra; usar `import { PgBoss } from 'pg-boss'`.
- teamSize/teamConcurrency e onComplete aparecem em quase todos os tutoriais antigos e NÃO existem mais (removidos no v10); o equivalente atual é batchSize/localConcurrency e deadLetter.
- retryLimit default agora é 2 (retry é opt-out): jobs não-idempotentes precisam de retryLimit:0 explícito.
- Apenas UMA instância pg-boss deve rodar com supervise ativo; instâncias web devem usar supervise:false (e schedule:false) para não duplicar manutenção/cron.
- schedule() usa cron de 5 campos (precisão de minuto); nomes de fila no v12 só aceitam [A-Za-z0-9._-].
- LISTEN/NOTIFY do pg-boss é incompatível com PgBouncer em transaction/statement pooling.
- Datas exatas dos releases 11.0.0/12.0.0 do pg-boss vieram com ano ambíguo no parse da página do GitHub (provavelmente set/2025 e nov/2025); o conteúdo das notas é confiável, as datas não.
- Preço dos embeddings: há discrepância documentada entre a doc (~$0.016/$0.106) e a pricing page ($0.02/$0.13); orçar pelo maior.
- Detalhes finos das versões 12.2x do pg-boss (detectSchemaDrift, redrive de DLQ, exclusive/key_strict_fifo, dashboard) vieram de fonte única (releases/doc master) — confirmar na doc oficial antes de depender deles em código.
=RECOMMENDATIONS=
- pgvector: NÃO usar o pacote da Ubuntu (0.6.0). Adicionar o repo PGDG (apt.postgresql.org) e instalar postgresql-16-pgvector (0.8.5-1.pgdg24.04+1); depois ALTER EXTENSION vector UPDATE (ou CREATE EXTENSION vector) em cada database. Build from source só se quiser evitar o repo PGDG.
- Embeddings: usar text-embedding-3-small (1536 dims, US$0.02/1M tokens) — para flashcards o ganho do 3-large raramente justifica 6.5x o custo; se usar 3-large, gravar como halfvec(3072) ou pedir dimensions:1536.
- Índice vetorial: começar SEM índice ANN (busca exata + btree em owner_id/user_id) dado o volume por usuário (milhares a dezenas de milhares); medir latência real. Se precisar de ANN, criar HNSW (m=16, ef_construction=64) e habilitar SET hnsw.iterative_scan = 'relaxed_order' nas queries filtradas por owner para evitar over-filtering; considerar halfvec_cosine_ops para reduzir tamanho de índice.
- pg-boss: instalar pg-boss@12 (12.26.1), import nomeado: import { PgBoss } from 'pg-boss'. Node 22.23.1 do servidor atende o mínimo 22.12. Criar filas explicitamente com createQueue() no bootstrap/migração, com deadLetter apontando para uma fila '<nome>.dlq'.
- Permissões DB: conceder GRANT CREATE ON DATABASE app TO app_role e deixar o pg-boss criar/migrar o schema pgboss no start(); em produção mais travada, gerar o SQL com o CLI do pg-boss (--dry-run/plans) e aplicar via migração, rodando a app com migrate:false.
- Topologia PM2 (sem Docker): dois apps no ecosystem.config — (a) 'web' = Next.js (pode ser cluster), instância pg-boss apenas para send/createQueue com supervise:false e schedule:false; (b) 'worker' = script Node dedicado (fork mode, instances:1 para começar) com start() + work() + schedule(), único com supervise ativo. Tratar SIGINT/SIGTERM chamando boss.stop() e aumentar kill_timeout do PM2 (~30s). Escalar workers aumentando localConcurrency/batchSize antes de aumentar instances (multi-master é seguro, mas 1 processo costuma bastar nessa escala).
- Retries/DLQ: confiar nos defaults retryLimit:2 e configurar retryBackoff:true + retryDelay para jobs de chamada à OpenAI; usar singletonKey (ex.: `embed-user-${userId}`) com singletonSeconds para debounce de reindexação por usuário.
- Se usar PgBouncer no futuro: não habilitar useListenNotify (exige conexão de sessão); manter polling (pollingIntervalSeconds default 2s já é ok para este caso).
