* [high] Drizzle has native RLS support since drizzle-orm@0.36.0 + drizzle-kit@0.27.0: pgRole(), pgPolicy() declared inside pgTable's third-argument array, .enableRLS() (0.45.x API), pgPolicy(...).link(existingTable), and drizzle-kit generates the CREATE POLICY / ALTER TABLE ... ENABLE ROW LEVEL SECURITY DDL in migrations.
  Schema shape (0.45.x): export const admin = pgRole('admin', {createRole:true, createDb:true, inherit:true}) or pgRole('admin').existing() for roles managed outside Drizzle; export const t = pgTable('users', {id: integer()}, (t) => [ pgPolicy('policy_name', { as: 'permissive'|'restrictive', to: roleRefOr'public', for: 'all'|'select'|'insert'|'update'|'delete', using: sql`...`, withCheck: sql`...` }) ]). Adding any pgPolicy to a table auto-enables RLS (no explicit enableRLS needed); .enableRLS() is for tables with RLS but no Drizzle-managed policies. Role management in migrations requires drizzle.config.ts: entities: { roles: true } (or {include/exclude/provider:'neon'|'supabase'}). drizzle-kit generate emits policies/roles DDL and migrate applies them. NOTE: in v1/RC docs the API is pgTable.withRLS('users', {...}) replacing .enableRLS(). Neon helper crudPolicy() via drizzle-orm/neon and Supabase predefined roles via drizzle-orm/supabase exist but are irrelevant for self-hosted PG16.
* [high] Recommended pool-safe RLS pattern: every user-scoped query runs inside db.transaction(), first statement sets context with set_config('app.user_id', $id, true) (third arg true = transaction-local) and optionally SET LOCAL ROLE, and the app connects with a dedicated runtime role that has NOBYPASSRLS, is NOT the table owner, and is not superuser.
  Canonical shape (Neon docs + rphlmr/drizzle-supabase-rls, both driver-agnostic): function rlsDb<T>(userId: string, cb: (tx) => Promise<T>) { return db.transaction(async (tx) => { await tx.execute(sql`select set_config('app.current_user_id', ${userId}, true)`); /* optionally: await tx.execute(sql`set local role app_user`); */ return cb(tx); }); } Policies then read current_setting('app.current_user_id', true)::uuid. Why the transaction is mandatory with a pool: set_config(..., true)/SET LOCAL revert automatically at COMMIT/ROLLBACK, so the connection returns to the pool clean; calling set_config outside a transaction (or with is_local=false / plain SET) leaks context to the next request that grabs that pooled connection — the classic RLS-leak bug. Drizzle's db.transaction pins one physical connection for the whole callback on both pg and postgres.js, so the set_config and the queries are guaranteed to hit the same connection. The rphlmr reference implementation additionally shows a two-client split: an 'admin' drizzle instance (privileged role, bypasses RLS, for jobs/webhooks/migrations) and a 'client' instance (restricted rls_client role) wrapped by createDrizzle(token, {admin, client}) exposing .rls(cb). Postgres-side hardening: table owners bypass RLS unless ALTER TABLE ... FORCE ROW LEVEL SECURITY, so make the runtime role a non-owner GRANTee; create it with NOSUPERUSER NOBYPASSRLS NOCREATEDB.
* [high] Prepared statements are not a problem for this stack (direct connection to local PG16, no external pooler): postgres.js's default prepared-statement caching and pg's parsing both work with SET LOCAL inside transactions. prepare:false is only needed behind transaction-mode poolers (PgBouncer/Supavisor).
  The prepare:false caveat repeatedly cited in RLS guides (rphlmr repo, Supabase docs) applies to transaction-mode connection poolers that don't support named prepared statements — not to a native pg.Pool/postgres.js pool talking directly to PostgreSQL, which is this project's setup (Ubuntu 24.04, PG16 nativo, PM2). Also note set_config parameters are passed as bind parameters ($1) fine; no need for raw string interpolation.

* [high] Driver recommendation for THIS stack: node-postgres (pg 8.22.0) with drizzle-orm/node-postgres, sharing a single pg.Pool with pg-boss. pg-boss 12.26.1 hard-depends on pg (^8.22.0) internally, so postgres.js would mean shipping two drivers.
  npm registry: pg-boss@12.26.1 dependencies include "pg": "^8.22.0" (engines node >=22.12, PostgreSQL 13+). pg-boss's constructor accepts a custom `db` option — any object implementing executeSql(text, values) => {rows, rowCount} (documented in pg-boss issue #444 and current docs) — and pg-boss 12.x additionally ships ORM adapters (Drizzle, Knex, Kysely, Prisma) so jobs can be enqueued inside an existing Drizzle transaction (transactional outbox: insert domain row + send job atomically). With drizzle-orm/node-postgres you build one pg.Pool, hand it to drizzle(pool) and to new PgBoss({db: {executeSql: (text, values) => pool.query(text, values)}}) or just let pg-boss make its own pool from the same connection string. SET LOCAL semantics are identical on both drivers (drizzle transaction = one checked-out client). postgres.js (3.4.9) is fine technically — sql.begin reserves one connection, RLS pattern works — but buys nothing here and adds a second driver. Grant note: pg-boss creates/uses its own 'pgboss' schema; run it under the privileged/admin role, not the RLS runtime role.
* [medium] @auth/drizzle-adapter (1.11.3) runs its queries as whatever role the drizzle instance you pass to DrizzleAdapter(db, ...) connects as — it has no concept of RLS or per-user context. Correct pattern: give the adapter a privileged/admin drizzle instance and keep the Auth.js tables (users, accounts, sessions, verification_token) WITHOUT RLS (or with policies only for the runtime role), applying RLS only to domain tables.
  The adapter executes createUser/getSessionAndUser/linkAccount etc. during sign-in and session checks — i.e., BEFORE an authenticated user context exists — so a set_config-scoped RLS transaction is impossible there by construction; it must run under a role that can freely read/write the auth tables. Practical setup for this app: two drizzle instances over roles: (1) app_admin (owner or full-GRANT role, NO RLS constraints) used by DrizzleAdapter, drizzle-kit migrate, and pg-boss workers; (2) app_user (NOSUPERUSER NOBYPASSRLS, non-owner, GRANT SELECT/INSERT/UPDATE/DELETE on domain tables) used by the rlsDb() transaction wrapper with set_config('app.current_user_id', session.user.id, true) taken from the Auth.js session in each server action / route handler. If you do want RLS on auth tables for defense-in-depth, add permissive policies TO app_admin (or rely on owner bypass) and never point the adapter at the restricted role — otherwise sign-in silently returns zero rows (default-deny). No official Auth.js doc prescribes RLS handling; this is the pattern consistent with how the adapter is implemented (it just consumes the db instance) and with the admin/client split shown in rphlmr/drizzle-supabase-rls.
* [medium] drizzle-kit push has had reported bugs applying RLS policies; generate + migrate is the reliable path for policies.
  GitHub issue drizzle-team/drizzle-orm#3504: 'RLS Policies not applied with push but applied with migrate'. Could not verify current fix status in this pass; treat push as unreliable for policy DDL and standardize on drizzle-kit generate + migrate in CI/deploy (which also matches a PM2/Ubuntu prod flow better than push).
=GOTCHAS=
- Context leak in the pool: set_config(name, value, false) or plain SET (without LOCAL) persists on the physical connection after it returns to the pool — the next request inherits another user's RLS context. Always set_config(..., true) or SET LOCAL, always inside db.transaction().
- set_config outside a transaction is useless with a pool: the next drizzle query may execute on a DIFFERENT pooled connection than the one that ran set_config.
- Table owner bypasses RLS silently unless ALTER TABLE ... FORCE ROW LEVEL SECURITY. If your runtime role owns the tables (common when one role runs migrations and the app), every policy is a no-op. Use separate migration/owner role vs runtime role, or FORCE RLS.
- Default-deny: enabling RLS on a table with no policy for the querying role returns zero rows with no error — pointing the Auth.js adapter (or pg-boss) at the restricted role breaks sign-in/jobs silently.
- current_setting('app.x') without the second arg true THROWS if the GUC was never set (e.g., admin console session); policies should use current_setting('app.current_user_id', true) and handle NULL.
- drizzle-kit push vs migrate divergence for policies (issue #3504): policies reported as applied by migrate but skipped by push. Use generate+migrate for anything RLS.
- The current https://orm.drizzle.team/docs/rls page documents the v1 API (pgTable.withRLS()); on stable 0.45.x the API is pgTable(...).enableRLS(). Copy-pasting v1 doc snippets into a 0.45 project fails to compile.
- views bypass RLS by default (run as view owner); PG15+ requires CREATE VIEW ... WITH (security_invoker = true) for RLS to apply through views.
- prepare:false on postgres.js is only needed behind transaction-mode poolers (PgBouncer/Supavisor) — not for this native-PG16 setup; adding it needlessly costs performance.
- drizzle-orm 1.0 removes RQBv1 and absorbs drizzle-zod: starting a new project today on 0.45.2 + relations() + drizzle-zod 0.8.3 means a real migration later (defineRelations, validators moved into core, migrations folder v3).
- pg-boss creates and manages its own 'pgboss' schema — run it under the privileged role; the RLS runtime role should have no access to that schema.
=RECOMMENDATIONS=
- Pin drizzle-orm 0.45.2 + drizzle-kit 0.31.10 for production now (matches the sibling projects' 0.45.x); do not start on 1.0.0-rc.4 unless willing to track RC churn — but write new relational queries minimally to reduce the RQBv1->defineRelations migration surface later.
- Declare RLS in-schema: pgRole for app_admin/app_user (use .existing() if roles are created by ops SQL), pgPolicy inside each domain pgTable with using/withCheck reading current_setting('app.current_user_id', true), and entities: { roles: {...} } in drizzle.config.ts; apply exclusively via drizzle-kit generate + migrate.
- Create two Postgres roles: app_admin (owner/migrations/Auth.js adapter/pg-boss) and app_user (NOSUPERUSER NOBYPASSRLS NOCREATEDB, non-owner, GRANTs on domain tables only); build two drizzle instances over one pg.Pool config and expose a rlsDb(userId, cb) wrapper: db.transaction -> tx.execute(sql`select set_config('app.current_user_id', ${userId}, true)`) -> cb(tx).
- Driver: use pg (node-postgres) 8.22.0 with drizzle-orm/node-postgres — pg-boss 12.x already depends on pg, allows sharing the pool via its db/executeSql option and its Drizzle adapter enables enqueueing jobs inside the same Drizzle transaction (outbox pattern).
- Leave Auth.js tables (users, accounts, sessions, verification_token) without RLS and served by the app_admin drizzle instance passed to DrizzleAdapter; derive userId from the Auth.js session in server actions/route handlers and pass it into rlsDb() for all domain queries (cards, decks, reviews).
- drizzle-zod 0.8.3 + zod 4.4.3 is a supported pairing — use it; no workaround needed.
- Add FORCE ROW LEVEL SECURITY to domain tables if any code path queries them as the owner role, and audit views with security_invoker=true.
